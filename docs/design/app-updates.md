# アプリの更新

[DESIGN.md](../../DESIGN.md) から分割した詳細です。Setup版の自動更新は [velopack-updates.md](velopack-updates.md)、配布物の梱包と検証は [release-packaging.md](release-packaging.md) にあります。

`src/update.rs` は利用者の明示操作で最新安定版を確認・取得します。Cloudflare R2の固定の公開URL（`https://skilvella.kagayoi.com/portable`）の `latest.json`（`{"schema":1,"version":"X.Y.Z"}`）から版だけを読み、先頭が数字の厳格な `MAJOR.MINOR.PATCH`（`v` 付き・プレリリース・未知の形式は拒否。未知のフィールドは無視）として検査し、現在版より新しい場合だけ適用します。OS同梱curlをシェルなしで起動し、HTTPS限定・取得時間・サイズを制限します。取得元は固定の1ホストだけを信頼し、リダイレクトは辿りません。同じ版の `portable/<版>/SHA256SUMS.txt` でアーカイブの整合性を確認します。配置は版付きの不変物（`portable/<版>/`）、README導線用の固定名、最後に置く `portable/latest.json` の3層で、タグ・GitHub Releaseは使いません。なお `versions/vX.Y.Z` などToolportランチャー引き継ぎのタグ表記はローカルの契約で、配布元とは無関係です。この経路の対象はWindows x64のZIP版とApple Silicon Macです。Windowsの `windows-installer` 機能付きビルド（Setup版）は配置をVelopackに委ねるため、この経路は使わず、[Velopackによる更新](velopack-updates.md) を使います（[Windowsの起動とサインイン登録](windows-startup.md)）。

`verify_archive` はアーカイブのサイズとSHA-256を検査し、Windows x64のZIPまたはApple Siliconのtar.gzから実行ファイルだけを取り出します。アーカイブ直下に対象の実行ファイル、`LICENSE`、`CHANGELOG.md`、`README.txt`、`BUILD-INFO.txt` が各1件そろっていることを求め、ファイル種別を検査します。実行ファイルのヘッダーで形式とCPUアーキテクチャを確認し、`BUILD-INFO.txt` の `version` を期待する版と照合します。アプリ内更新では `latest.json` が示す更新先の版を期待する版にします。

適用はプロセス内の単一起動制御とOSファイルロックを通します。稼働中の実行ファイルと同じフォルダーに専用ステージを作り、そこに複製した現行バイナリをヘルパーとして起動します。ヘルパーの検証完了後にHTTP/MCPを正常終了し、処理中の操作を待ちます。更新処理はLibraryや利用者スキルを変更しません。旧プロセスの終了後、通常配置では旧版のハッシュを再検査し、復旧用コピーを残して同一ファイルシステム上で置換します。Windowsでは、旧プロセスの終了直後に実行ファイルが解放されていないか、ウイルス対策ソフトが一時的に掴んでいて置換が `ERROR_ACCESS_DENIED`・`ERROR_SHARING_VIOLATION` で失敗することがあるため、この2つに限り約10秒まで再試行します。それ以外の失敗や時間切れは失敗として旧版の復元・再起動へ回します。Toolport最新ランチャーの配下では既存の版を維持し、新版の `install.json` と `cache.json` の検証情報を整合させて参照を切り替えます。新しいプロセスの起動に失敗した場合は、参照または旧バイナリの復元を試みます。更新完了後の起動時障害・OS電源断からの自動復旧は保証せず、ステージとログを保持します。

通常配置のヘルパーは再起動先を起動した後に終了します。Windowsではヘルパーの標準エラーに割り当てた `update.log` のハンドルを継承不可にし、再起動したアプリがログを開いたままにするのを防ぎます。

更新後に残る自分の一時物（更新ステージと自動更新設定の保存途中の一時ファイル）は、起動ごとに1回、専用スレッドで条件を満たすものだけ片付けます。条件と対象は [update-cleanup.md](update-cleanup.md) にあります。

設定画面の更新操作はJavaScriptだけが呼ぶため、CSRFトークン不一致も `reload: true` 付きのJSON（403）で返します。アプリの再起動でトークンが作り直されるので、開いたままの古い画面からの操作を接続障害と区別して再読み込みを案内するためです。インストール要求の受理後、画面は `/settings` を2秒間隔で最長180秒取得し、`data-version` の起動中の版が更新前から変わり、期待する版と一致したら自動で再読み込みします。再起動中の接続失敗は待機として扱い、時間切れでは手動の再読み込みを案内します。

Toolport管理下では旧アプリの終了後にランチャーと同じ起動ロックを取得し、新版の終了まで保持します。取得できなければ適用も参照変更も行いません。Windowsのロック名はランチャーの.NETパス正規化に合わせ、通常パスの8.3短縮名を長い名前へ展開し、拡張パスはそのまま扱います。ロック名の互換性を保つため、非ASCII文字を含むToolport管理先では適用開始前に拒否し、短縮名の展開後も同じ条件を確認します。
